# FR100 lexical retrieval qualification — X399, 2026-11-02

The 100 long synthetic texts were imported and queried in an isolated directory
on Memory-engine-tests. Neither the production canonical memory nor its index
was changed. FTS5 remains experimental: it returned exactly the same ordered
top-five document IDs as the reference index, with higher latency in this run.

## Sources and method

- Integration base: `250378e44a9458eafa049d33ff8ac05164cc40a3` (audit CI).
- Existing FTS5 work: `ed25fe7f335ff0c37df7bffe2a1b29bdd8991f61` (C198–C208).
  This includes the verified adapter, generation serialization and publication
  receipts. The earlier impression that this work consisted of two initial
  files was incomplete. It has not been enabled in the production runtime.
- Benchmark code commit: `204026e2e33b5c3ceece1150a12838eeb2f00d99` on the VM.
- FR100 v1: 100 documents, 236,091 words; 1,000 questions, including 900
  answerable questions and 100 negative controls. No tokenizer was measured.
- Batches contain the first 10, 50 and 100 documents and their 100, 500 and
  1,000 questions. They overlap; they are not independent repetitions.
- All document hashes checked against the manifest. Only question text enters
  retrieval. Expected answers stay on the X399 host and are scored separately.
- Whole documents are stored as canonical memories. The reference is
  `InMemoryIndex`; the candidate is `VerifiedSqliteFts5Index`.
- One sequential run, 8 vCPU / 16 GiB guest. Reference runs before FTS5 in each
  batch. Results are descriptive, not statistical performance estimates.

## Results

| Documents | Questions per adapter | Reference p50 / p95 | FTS5 p50 / p95 | All required evidence in top 5 |
|---:|---:|---:|---:|---:|
| 10 | 100 | 13.25 / 14.00 ms | 15.13 / 16.11 ms | 100% of 90 |
| 50 | 500 | 66.87 / 69.69 ms | 72.13 / 75.69 ms | 98.22% of 450 |
| 100 | 1,000 | 132.47 / 139.13 ms | 143.33 / 150.82 ms | 83.33% of 900 |

Ordered top-five parity: 1,600/1,600 comparisons. There were 3,200 retrievals
across both adapters, plus 60 post-restoration checks. At 100 documents, FTS5
query total is 143.57 s versus 132.60 s (+8.27%); the SQLite file is 4,341,760
bytes. Whole-process peak RSS is 44,024 KiB, not a per-adapter memory comparison.

For every batch, duplicate identities were refused, canonical hashes stayed
unchanged, archive restoration reproduced the canonical manifest, and ten
queries per adapter gave identical results after rebuilding from the restore.
This checks a file archive restore; it is not a whole-VM disaster recovery test.

At 100 documents, evidence recall@5 is 100% for exact questions, 99% for
paraphrases, 46% for temporal questions and 10% for obsolete-value questions.
All 50 cross-document questions retrieve both required documents. Overall
document recall@1 is 73.89%, recall@5 83.33%, MRR@5 0.7905.

Concrete regression candidates:

- `Q-0004` explicitly asks for the provisional value in `DOC-001` (71). The
  top five are `DOC-091` to `DOC-095`; the required document is absent.
- `Q-0003` asks for the corrected final value in `DOC-001` (67). The top five
  are `DOC-006`, `DOC-019`, `DOC-026`, `DOC-047`, `DOC-068`.

The shared lexical ranker splits identifiers into word tokens and does not
enforce an explicitly requested document as a source constraint. Repeated
boilerplate competes with identity terms. This is a code-based explanation to
investigate, not a proven complete causal analysis or a deployed correction.

All 100 negative controls returned candidates. A retrieval candidate is not
an answer: this does not measure hallucinations or successful abstention.

## Limits and next tests

This is a fixed synthetic corpus with repetitive templates and explicit IDs,
not an independent natural-language holdout. Questions and answers come from
the same corpus generator. No LLM answer generation, semantic embedding,
Qdrant search, temporal conflict resolution or answer grounding was evaluated.
FTS5's candidate floor exceeds this corpus size; a larger selective workload
is needed before judging its scaling benefit. Current C208 tests do not prove
power-loss recovery or safety under every hot-WAL/concurrent-writer scenario.

Next: add explicit-source retrieval regression cases, then entity/time-aware
evidence selection with independent paraphrases and negative controls. Compare
larger corpora with repeated randomized adapter order before promoting FTS5.

## Reproduction and evidence

Run in this branch, with a fresh output path and a document-only corpus copy:

```bash
python -m tools.evaluation.run_long_corpus \
  --corpus-root /path/eidolon-corpus-fr-100-v1 \
  --questions /path/questions.jsonl --work /path/new-run
```

Copy retrieval outputs to the separate evaluation host, then:

```bash
python tools/evaluation/score_long_corpus.py \
  --run /path/new-run --oracle /path/evaluation/answers.jsonl
```

Machine-readable `summary.json` and `quality.json` accompany this report. Raw
outputs and restored files are retained on the X399 host at
`/home/toytoy/eidolon-validation/corpus-20261102/run-1` and on the test VM.
The input manifest and question SHA-256 values are recorded in `summary.json`.
The answer oracle must never be copied into the indexed canonical directory.
