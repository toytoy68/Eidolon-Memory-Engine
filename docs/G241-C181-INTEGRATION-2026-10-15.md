## C181 et patch 0037

Les trois sondes de reconstruction sont intégrées avec attribution et ajoutées
au workflow Qdrant ciblé. Le patch original est conservé intégralement dans Core.
Trois sondes vertes telles que reçues ; 61 tests sondes/adaptateur/projection
réussis ensuite avec -W error. Deux mutations indépendantes ont été reproduites :
retirer la preuve du point reconstruit provoque 3 échecs ; retirer le verrou
canonique provoque 1 échec. La source applicative est restaurée octet pour octet
après chaque mutation et n'est pas modifiée dans ce lot.

Une assertion du troisième test comparait la fin de l'écrivain à un timestamp
pris par l'autre thread après le retour de rebuild. Or l'écrivain peut finir
légitimement après libération du verrou mais avant le réveil de l'appelant.
Un délai de 50 ms à cet endroit reproduit un échec sur le code correct. La sonde
vérifie désormais l'absence de fin d'écriture pendant les embeddings, avec un
signal indiquant la tentative de l'écrivain, puis vérifie sa fin et les révisions
respectives canon/index. Le délai après retour reste présent pour couvrir cet
ordonnancement valide. Le mutant sans verrou reste détecté.

Compromis confirmé : rebuild tient le verrou canonique pendant toute la
reconstruction, embeddings compris. Les écrivains coopératifs attendent ; aucune
promesse de faible latence sur gros corpus n'est déduite de ces tests.

C181 ajoute aussi cinq tests Core de jeton (propriétaires, bornes, liens). Ils sont
intégrés sans modification. Ici 13 tests de jeton passent, deux changements de
propriétaire échouent avec EINVAL dans le conteneur malgré uid 0 ; ce n'est pas une
validation des contrôles concernés. Une étape CI Core dédiée exécute les cinq
sondes en root avec de vrais changements d'UID sur fichiers synthétiques. Résultat
requis avant de les compter réussies ; aucune permission de secret réel modifiée.

## G240 : première recette rouge, frontière d'effet corrigée

Workflow serveur 38663756814 : **11 réussis, 2 échecs**, 68,93 s. Le backlog de
1200 documents et la panne réelle au milieu d'une page passent. Les deux échecs
viennent du proxy : le premier PUT /points est l'invalidation du descripteur,
pas l'écriture du document. L'acquittement était bien coupé, mais avant le point
que le test attendait à tort comme déjà écrit. Aucun contournement du worker.

Le proxy sélectionne désormais explicitement `payload.kind` : `descriptor` ou
`information`. Chacun est testé en déconnexion et timeout. Après coupure de
réponse du descripteur, aucun point Information n'existe ; la reprise le crée,
avec un nouveau calcul normal. Après coupure de réponse du document, le point
existe ; la reprise l'adopte sans ré-encodage. PUBLISHED reste en attente jusqu'à
preuve. **15 scénarios serveur** au total ; résultat corrigé à récupérer en CI.
